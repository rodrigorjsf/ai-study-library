## Onde as regras moram no Cursor IDE e em que ordem se aplicam?

### Takeaway

No IDE, as regras de conversa do Agent são quatro tipos de produto (Project Rules em `.cursor/rules/*.mdc`, User Rules, Team Rules, `AGENTS.md`), mais `CLAUDE.md` / `CLAUDE.local.md` tratados como `AGENTS.md`, mais o legado `.cursorrules`. A única ordem de precedência escrita para conflito é **Team Rules → Project Rules → User Rules**. `AGENTS.md` aninhado não entra nessa frase: o doc diz que o mais específico prevalece sobre o pai. Isso é o IDE. O SDK não herda essa pilha inteira sem `settingSources`.

### Cited Findings

- Quatro tipos na página de regras, baixada em 2026-11-17 de [https://cursor.com/docs/rules.md](https://cursor.com/docs/rules.md): Project Rules em `.cursor/rules` (versionadas); User Rules globais, usadas por Agent (Chat); Team Rules no dashboard, planos Team e Enterprise; `AGENTS.md` como alternativa simples a `.cursor/rules`. [DOC](https://cursor.com/docs/rules.md)
- Conteúdo aplicado entra no início do contexto do modelo. [DOC](https://cursor.com/docs/rules.md)
- Project rule tem de ser `.mdc`. Um `.md` solto em `.cursor/rules` é ignorado porque não tem frontmatter (`description`, `globs`, `alwaysApply`). Markdown puro deve ir para `AGENTS.md`. [DOC](https://cursor.com/docs/rules.md)
- Matriz do frontmatter, mesma página: `alwaysApply: true` inclui sempre e ignora globs e description; `alwaysApply: false` com `globs` anexa quando um arquivo que casa está no contexto; `alwaysApply: false` com `description` e sem globs fica para o Agent puxar quando achar relevante; os dois omitidos só entram com `@`-mention no chat. [DOC](https://cursor.com/docs/rules.md)
- `globs` aceita vários padrões separados por vírgula (exemplo documentado: `docs/**/*.md, docs/**/*.mdx`). [DOC](https://cursor.com/docs/rules.md)
- Menção `@arquivo` dentro da regra não inline o arquivo. O Agent lê com as tools. O doc diz que isso é igual no editor, no CLI e em Cloud Agents. [DOC](https://cursor.com/docs/rules.md)
- Regras não afetam Cursor Tab nem outras features de AI. [DOC](https://cursor.com/docs/rules.md)
- Team Rules: texto livre, sem a pasta de Project Rules; glob opcional (sem glob, valem em toda conversa); com glob, só quando um arquivo que casa está no contexto. Ativação: "Enable this rule immediately" e "Enforce this rule" (enforced não pode ser desligada em Customize). Precedência escrita: **Team Rules → Project Rules → User Rules**. Todas as aplicáveis são mescladas; a fonte anterior prevalece quando a orientação conflita. [DOC](https://cursor.com/docs/rules.md)
- Regras não são importadas sozinhas de um repositório. Entram por plugin publicado num marketplace (`.cursor-plugin/marketplace.json` ou team marketplace). [DOC](https://cursor.com/docs/rules.md)
- `AGENTS.md` na raiz e em subdiretórios. Aninhados combinam com os pais; "more specific instructions taking precedence". Sem frontmatter. [DOC](https://cursor.com/docs/rules.md)
- User Rules: **Customize → Rules**, valem em todos os projetos, usadas por Agent (Chat). A página de regras não dá path de arquivo. [DOC](https://cursor.com/docs/rules.md)
- Ajuda, baixada no mesmo dia de [https://cursor.com/help/customization/rules.md](https://cursor.com/help/customization/rules.md): User Rules de Customize ficam na conta Cursor e sincronizam no login; **não** entram em profile export. Arquivos em `~/.cursor/rules` (Windows: `%USERPROFILE%\.cursor\rules`) ficam na máquina e não sincronizam. Team Rules ficam nos servidores da Cursor (dashboard). A mesma precedência Team > Project > User. [DOC](https://cursor.com/help/customization/rules.md)
- `.cursorrules` na raiz é legado e "will be deprecated". Migrar para uma rule **Always Apply**. [DOC](https://cursor.com/help/customization/rules.md)
- "`Cursor reads CLAUDE.md files the same way it reads AGENTS.md`." `CLAUDE.md` é sempre aplicado em toda conversa, "regardless of any `alwaysApply` frontmatter". Condicional fica em `.cursor/rules`. [DOC](https://cursor.com/help/customization/rules.md)
- Duas rules com o mesmo filename em pastas diferentes são identidades pelo path completo; não há override por nome. [DOC](https://cursor.com/help/customization/rules.md)
- A página de regras do IDE **não** coloca `AGENTS.md` nem `CLAUDE.md` na frase Team → Project → User. [DOC](https://cursor.com/docs/rules.md)

## O que `Agent.create` e `Agent.resume` aceitam para regras, prompt e `settingSources`?

### Takeaway

`Agent.create(options: AgentOptions)` e `Agent.resume(agentId, options?: Partial<AgentOptions>)` não têm `rules`, `instructions` nem `system` separado. O único texto de sistema é `systemPrompt?: string`, e ele substitui o prompt interno do Cursor sem apagar rules e skills. Camadas de disco são `local.settingSources`, opt-in, só no runtime local. Cloud ignora o campo.

Não liga o walker de `AGENTS.md` (isso é `project`) nem o bloco de hooks (hooks exigem `project`, `user` ou `mdm`).
- `"mdm"` sozinho liga hooks de enterprise e não liga `localExtensibility` (rules/skills), porque `mdm` não entra na condição `R`.
- User Rules da conta e Team Rules do dashboard não são o layer `"user"` nem o layer `"team"` visíveis neste cliente. `"user"` é `~/.cursor/` (e o `settings.json` do Claude em home). `"team"` neste binário é, no máximo, managed skills via dashboard.

### Gaps

- Não confirmei se o backend, depois do `send`, injeta User Rules e Team Rules por causa da API key. O cliente publicado não as busca. A doc do SDK não diz que as injeta.
- `repoHooks` aparece num flatten (`projectHooks`, `claudeProjectHooks`, `claudeProjectLocalHooks`). Não tracei quem preenche. Pode ser o caminho de team hooks; não está provado.
- Aplicação de `globs` / "Apply Intelligently" / `@`-mention manual depois que o arquivo foi parseado não está no walker. O frontmatter segue no objeto. Não há API de `@mention` no SDK.
- Não reexecutei um agente. Medições antigas no starter não entram aqui como confirmação.

## O que não se herda, e o que o autor do workflow teria de passar

### Takeaway

Um passo local do SDK com `settingSources` omitido ou `[]` não fica igual ao turno do IDE. Para chegar perto do contexto de projeto é preciso `local.settingSources` contendo `"project"` (e `"user"` / `"mdm"` / `"plugins"` se esses layers importam). User Rules da conta, Team Rules, rules manuais por `@`, e o texto que o usuário vê como "always applied" no Customize não têm campo. O autor cola isso no prompt do passo ou aceita não tê-los. `systemPrompt` não é o veículo: ele apaga o prompt do harness e ainda depende dos layers para as rules de disco.

### Cited Findings

- Sem `settingSources`, o parser deixa todos os flags falsos e a doc diz que só MCP inline carrega. [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/305.js) [DOC](https://cursor.com/docs/sdk/typescript.md)
- IDE aplica sempre as rules com `alwaysApply: true`, e a ajuda diz o mesmo de `CLAUDE.md`, sem o Agent decidir. Isso só existe no SDK se o arquivo foi carregado (`"project"`) e o runtime respeitar o frontmatter. O walker marca `AGENTS.md` e `CLAUDE.md` com `alwaysApply: true`. Não há prova nesta leitura de que o servidor inclui o corpo em todo turno headless do mesmo jeito que o chat. [DOC](https://cursor.com/docs/rules.md) [DOC](https://cursor.com/help/customization/rules.md) [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/305.js)
- Rule "Apply Manually" (`alwaysApply: false`, sem description e sem globs) só entra com `@`-mention no chat. `AgentOptions` não tem campo de menção. [DOC](https://cursor.com/docs/rules.md) [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/options.d.ts)
- Glob de Project Rule e de Team Rule depende de "matching files in context". Um passo cujo turno não traz esses arquivos no contexto não dispara a rule, pela regra do IDE. O SDK não oferece um override para forçar o glob. [DOC](https://cursor.com/docs/rules.md)
- Team Rules enforced vêm do dashboard e "cannot be disabled in Customize". O layer `"team"` do SDK 1.3.1 não lê `includeTeamExtensibility`. Não há opção para injetar o texto da Team Rule. [DOC](https://cursor.com/docs/rules.md) [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/305.js)
- User Rules de Customize estão na conta, não num arquivo do repo, e sincronizam no login do app. O SDK "doesn't auto-discover credentials from a local Cursor app installation". [DOC](https://cursor.com/help/customization/rules.md) [DOC](https://cursor.com/docs/sdk/typescript.md)
- Cloud sempre carrega `project` / `team` / `plugins` e ignora `settingSources`. `user` e `mdm` "have no VM equivalent". `systemPrompt` com cloud lança `ConfigurationError`. [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/options.d.ts) [DOC](https://cursor.com/docs/sdk/typescript.md)
- Com `local.fs`, hooks não rodam qualquer que seja `settingSources`; skills e `AGENTS.md` aninhado não são descobertos; rules de projeto saem só da árvore e só com `"project"`. [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/options.d.ts) [PKG](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/README.md)
- Inline `mcpServers` não persistem em `Agent.resume`. Hooks não têm callback programático. [DOC](https://cursor.com/docs/sdk/typescript.md)

### Inferences

- Para um passo local parecer o turno do IDE no mesmo checkout, o mínimo explícito no código é `local: { cwd, settingSources: ["project"] }` se bastam rules, `AGENTS.md`, `CLAUDE.md`, hooks e MCP do projeto. Acrescentar `"user"` para `~/.cursor/hooks.json`, `~/.cursor/mcp.json` e skills de home; `"mdm"` para `/etc/cursor/hooks.json`; `"plugins"` para MCP/skills de plugin. `"all"` liga os cinco, mas não pode ser misturado. Nada disso entrega User Rules da conta nem Team Rules.
- O que não tem arquivo no repo (User Rules da conta, Team Rules, uma rule manual) tem de ir no texto do `send` da etapa, ou num `AGENTS.md` / `.mdc` com `alwaysApply: true` que o `"project"` já carrega. `systemPrompt` é outro eixo: substitui a identidade do harness e exige opt-in da conta.

### Gaps

- Não há medida, nesta sessão, de se uma rule `alwaysApply: true` carregada pelo SDK entra no prompt do modelo ou só fica disponível para o modelo puxar. O IDE diz "included". O pacote só mostra o load.
- Comportamento de glob quando o passo não abre arquivo: não medido.
- Se o backend anexa Team Rules a um run local autenticado com API key de usuário de time: não está no cliente nem na página do SDK.

## Como o Claude Code carrega `CLAUDE.md`, rules e settings num passo headless ou de workflow, e onde difere do Cursor?

### Takeaway

No Claude Code, `claude -p` carrega `CLAUDE.md`, rules, hooks, skills, MCP e auto memory como uma sessão interativa, a menos que `--bare` desligue essa descoberta. Um `agent()` de workflow é um subagent: a página de subagents diz que ele recebe a hierarquia de `CLAUDE.md` (e o `AGENTS.md` que a sessão tiver carregado), com Explore, Plan e `omitClaudeMd` como exceções. A mesma página também diz, noutro ponto, que `omitClaudeMd` não impede o load. No Cursor SDK local é o inverso do default: nada de disco até `settingSources`, e `AGENTS.md` e `CLAUDE.md` entram juntos quando `"project"` está ligado, em vez do "um ou outro" do Claude Code.

### Cited Findings

- `claude -p` sem `--bare` "discovers and loads them as an interactive session would", inclusive o que está no cwd e em `~/.claude`: hooks, skills, commands, subagents, plugins, MCP, auto memory e `CLAUDE.md`. Um `-p` roda hooks de `.claude/settings.json` e conecta `.mcp.json` mesmo em pasta não trusted, sem diálogo de trust. [DOC](https://code.claude.com/docs/en/headless.md)
- `--bare` pula essa descoberta (hooks, skills, commands, subagents, plugins, MCP, auto memory, `CLAUDE.md`). Exceção parcial: skills de um `--add-dir` em `.claude/skills/` ainda carregam; `.claude/commands/` e `.claude/agents/` desse dir não. Hooks continuam desligados mesmo se passados com `--settings` ou por plugin. Para prompt, `--append-system-prompt` ou `--append-system-prompt-file`; settings via `--settings`; MCP via `--mcp-config`; agents via `--agents`. O doc diz que `--bare` é o modo recomendado para script e SDK e "will become the default for `-p`". Antes de v2.1.286 o bare era parcial. [DOC](https://code.claude.com/docs/en/headless.md)
- Settings, maior precedência primeiro: managed (arquivo, MDM ou server-managed) → command line (`--settings` acima de user/project/local e abaixo de managed) → project local (`.claude/settings.local.json`) → shared project (`.claude/settings.json`) → user (`~/.claude/settings.json`). Variável de ambiente não é um nível dessa pilha; o par env/key é decidido por chave. [DOC](https://code.claude.com/docs/en/settings.md)
- `CLAUDE.md`, ordem de load da tabela (escopo mais largo primeiro, instrução de projeto aparece depois da de usuário): managed (`/etc/claude-code/CLAUDE.md` em Linux e WSL; `/Library/Application Support/ClaudeCode/CLAUDE.md` no macOS; `C:\Program Files\ClaudeCode\CLAUDE.md` no Windows) → user `~/.claude/CLAUDE.md` → project `./CLAUDE.md` ou `./.claude/CLAUDE.md`. Arquivos do cwd e de cada ancestral são concatenados, da raiz do filesystem até o cwd; no mesmo diretório, `CLAUDE.local.md` vem depois de `CLAUDE.md`. Subdiretórios carregam quando o Claude lê ou edita um arquivo lá, não no launch. Comentário HTML de bloco é removido antes de injetar. [DOC](https://code.claude.com/docs/en/memory.md)
- `.claude/rules/*.md` sem `paths` carregam no launch com a mesma prioridade que `.claude/CLAUDE.md`. `paths` é o único campo de frontmatter lido; o resto é ignorado. Rules de projeto são puladas se `project` está fora de `--setting-sources`. Antes de v2.1.211, rules on-demand carregavam mesmo com `project` excluído. `CLAUDE.local.md` de um `--add-dir` é pulado se `local` está fora de `--setting-sources`. [DOC](https://code.claude.com/docs/en/memory.md)
- `AGENTS.md` no Claude Code, default `claude-md-or-agents-md`, exige v2.1.277+: lê `AGENTS.md` só se não houver `CLAUDE.md`, `.claude/CLAUDE.md` ou `CLAUDE.local.md` no cwd ou acima. Não contam para esse bloqueio: `~/.claude/CLAUDE.md`, o `CLAUDE.md` managed e `.claude/rules/`. Modo `claude-md-and-agents-md` lê os dois e não relê um `AGENTS.md` já importado ou com o mesmo inode. `claude-md` só `CLAUDE.md`. `managed-only` só o managed e auto memory no launch. O modo mora em `pluginConfigs` de `cc-plugin-agents-md@builtin` (antes de v2.1.285 o id era `agents-md@builtin`), lido de user, `--settings` ou managed, ignorado em project e local settings. [DOC](https://code.claude.com/docs/en/memory.md)
- Import `@path` expande junto do `CLAUDE.md`. Dentro de crase ou fence não importa. [DOC](https://code.claude.com/docs/en/memory.md)
- Subagents: "Each inherits the parent conversation's permission rules". Explore e Plan começam sem `CLAUDE.md` e sem git status. Outros built-in e custom "load both, unless you set `omitClaudeMd`". [DOC](https://code.claude.com/docs/en/sub-agents.md)
- `omitClaudeMd: true` (v2.1.271+): "start this subagent without the user, project, and local CLAUDE.md files"; managed policy ainda carrega, exceto em managed subagents. Ignorado se o agent é a sessão principal via `--agent` ou a setting `agent`. [DOC](https://code.claude.com/docs/en/sub-agents.md)
- "What loads at startup": a hierarquia inteira que a conversa principal carrega, incluindo `~/.claude/CLAUDE.md`, project rules, `CLAUDE.local.md`, managed, e `AGENTS.md` carregado como instrução de projeto. Explore e Plan pulam. `omitClaudeMd` carrega só managed, ou nada se a definição vem de managed settings. `CLAUDE.md` de subdiretório e rules com `paths` ainda carregam on demand para Explore, Plan e `omitClaudeMd`. [DOC](https://code.claude.com/docs/en/sub-agents.md)
- Contradição na mesma página, baixada 2026-11-17: a seção do system prompt do subagent diz que "`CLAUDE.md` files and project memory still load through the normal message flow, even when the agent's definition sets `omitClaudeMd`". O campo e "What loads at startup" dizem o oposto para user/project/local. [DOC](https://code.claude.com/docs/en/sub-agents.md)
- Um prompt de subagent custom substitui o system prompt default do Claude Code, "the same way `--system-prompt` does". [DOC](https://code.claude.com/docs/en/sub-agents.md)
- Workflows: `agent()` cria um subagent; o script orquestra. A página baixada não nomeia `CLAUDE.md`, `omitClaudeMd` nem `--setting-sources`. Permissões do subagent do workflow seguem as permission rules da sessão. [DOC](https://code.claude.com/docs/en/workflows.md)
- O system prompt do Claude Code "isn't published". Instrução permanente é `CLAUDE.md` ou `--append-system-prompt`. [DOC](https://code.claude.com/docs/en/settings.md)

### Inferences

- Um passo de workflow do Claude Code, sendo subagent e não Explore/Plan, leva `CLAUDE.md` por default. O autor desliga com `omitClaudeMd` no subagent, ou a sessão inteira com `--bare` / `managed-only`. Não há, na página de workflows, um equivalente de `settingSources` por `agent()`.
- Diferença de default que muda o desenho do passo: Claude Code headless carrega instrução de projeto salvo opt-out (`--bare`, excluir `project` em `--setting-sources`, `omitClaudeMd`). Cursor SDK local não carrega salvo opt-in (`settingSources` com `"project"`).
- Diferença de arquivo: Claude Code escolhe `CLAUDE.md` ou `AGENTS.md` (default exclusivo; os dois só no modo `claude-md-and-agents-md`, com dedup de import/symlink). O walker do Cursor SDK 1.3.1, com third-party forçado em true, carrega os dois e só deduplica inode ou texto igual. Um `CLAUDE.md` que faz `@AGENTS.md` é import no Claude Code; no Cursor a ajuda não descreve `@` de `CLAUDE.md` como import, e o pacote não mostra esse expand.
- Diferença de rules com glob: Claude Code usa `paths` em `.claude/rules/*.md` e ignora outro frontmatter. Cursor IDE usa `globs` + `alwaysApply` + `description` em `.mdc`. O SDK não traduz um no outro.
- Diferença de prompt: Claude Code tem `--append-system-prompt` (soma) e `--system-prompt` / prompt de subagent (substitui, e a página diz que `CLAUDE.md` ainda entra pelo fluxo de mensagens). Cursor SDK tem só `systemPrompt` substituto, local, com gate de conta, e o `.d.ts` diz que rules e skills continuam como contexto ambiente.
- Diferença de admin: Claude Code managed settings vencem user/project e há `CLAUDE.md` managed em `/etc/claude-code/CLAUDE.md`. Cursor separa Team Rules (dashboard, precedência sobre project e user) de hooks MDM (`/etc/cursor/hooks.json`, layer `"mdm"`). Não achei `CLAUDE.md` managed do Cursor nem Team Rules no cliente do SDK.

### Gaps

- A contradição de `omitClaudeMd` na própria página de subagents ficou sem terceira fonte nesta sessão. Não dá para dizer qual frase o binário atual obedece.
- Não baixei `cli-reference` para a lista fechada de valores de `--setting-sources`. `memory.md` nomeia `project` e `local` apenas.
- `workflows.md` não diz se o `agent()` do script pode setar `omitClaudeMd`. A ponte é a página de subagents, não uma frase da página de workflows.
- Não comparei versões instaladas do Claude Code nesta máquina. As versões citadas (v2.1.211, v2.1.271, v2.1.277, v2.1.285, v2.1.286) são as que as páginas ao vivo nomeiam em 2026-11-17.
