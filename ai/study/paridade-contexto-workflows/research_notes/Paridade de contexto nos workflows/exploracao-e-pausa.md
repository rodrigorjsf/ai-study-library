Espelho local de `ai/docs/cursor/` datado 2026-11-11. Em 2026-11-17, `curl` das páginas vivas devolveu HTTP 200: [workflows.md](https://code.claude.com/docs/en/workflows.md) (45 412 bytes), [sdk/typescript.md](https://cursor.com/docs/sdk/typescript.md) (125 390 bytes), [mcp.md](https://cursor.com/docs/mcp.md) (18 709 bytes). Dois processos distintos: o agente do chat do Cursor IDE, e o job do `cursor-workflows-starter` (processo destacado). O job não escreve no chat. O chat só vê o que uma tool MCP ou o stdout de um comando de shell devolverem ao turno que os chamou.

## O que um resultado de tool MCP ou o stdout da CLI carregam de volta ao turno do agente do Cursor IDE (tamanho, forma, quem fala depois)

### Takeaway
O canal de volta é pull e textual: `wait_workflow` / `get_workflow_status` devolvem um único bloco MCP `text` com o JSON do `JobState`; `wf wait` e `wf status` imprimem esse mesmo JSON no stdout; `wf run` em primeiro plano imprime o `RunOutcome`. Não há teto de bytes documentado para esse JSON. O progresso (`recent`) é capado; o `result` do workflow vai inteiro. Quem fala depois da tool é o modelo do chat, não o workflow.

### Cited Findings
- O servidor MCP `cursor-workflows` (`packages/runtime/src/mcp-server.ts`) responde com `{ content: [{ type: "text", text: JSON.stringify(v, null, 2) }] }`. Falha de handler leva o mesmo JSON mais `isError: true` e corpo `{ "error": "..." }`. Falha que o SDK MCP rejeita antes do handler não é JSON: `MCP error -32602: ...`. O stdout do processo do servidor é o canal JSON-RPC; console do SDK vai para stderr. — [mcp-server.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/mcp-server.ts)
- Tools e o que cada uma devolve: `list_workflows` (meta de cada workflow); `start_workflow` → `{ jobId, runId, next: "call wait_workflow with this jobId", dashboardUrl?, dashboardWarning?, violations? }`, sem esperar o run; `wait_workflow` espera e devolve o estado; `get_workflow_status` o mesmo estado sem espera; `cancel_workflow` cancela e devolve o estado. `timeoutSec` de `wait_workflow` é clampado a 1..50; ausente ou `null` vira 45. — [mcp-server.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/mcp-server.ts), [job-state.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/job-state.ts) (`WAIT_MAX_SEC = 50`)

### Inferences
- Inferência: o “quem fala depois” no chat é sempre o agente do IDE. Com `status: running`, o próximo ato previsto pela skill é outra tool (`wait_workflow`), não uma pergunta ao usuário. Com `status: finished`, o próximo ato previsto é uma mensagem do assistente ao usuário; a fala seguinte é a da pessoa. O workflow já terminou o processo nesse momento.
- Inferência: um `result` grande (relatório, lista de seams) entra inteiro no contexto do turno que chamou `wait_workflow` ou leu o stdout. O único corte automático no caminho IDE é o de `recent`, não o do artefato.

### Gaps
- Número do timeout de tool MCP no chat do Cursor IDE, e número de bytes em que o IDE ou o SDK truncam um resultado de tool. A flag `truncated` existe; o limiar não está nas páginas buscadas.
- Número oficial do timeout de comando no shell do agente do IDE. O guia de terminal espelhado não traz.

## Quais primitivas de resume e journal existem no `@cursor/sdk` (`Agent.resume`, id de conversa) e no cursor-workflows-starter (journal, jobs, state), e se um turno posterior do IDE consegue entregar a resposta da pessoa a um run retomado

### Takeaway
São duas retomadas que não se substituem. `Agent.resume(agentId)` religa um agente do SDK (`agent-<uuid>` local, `bc-<uuid>` cloud). O starter retoma um workflow por `resumeRunId` / `--resume`, reusando o journal em `.workflows/runs/<runId>/journal.jsonl` e abrindo um job novo. A resposta da pessoa não entra por `Agent.send` no agente da etapa: o turno seguinte do chat chama `start_workflow` de novo, com `resumeRunId` e os args de aprovação. O código do workflow lê esses args.

### Cited Findings
- `Agent.resume(agentId, options?)` devolve um `SDKAgent`. O runtime é o prefixo do id: `bc-` é cloud, qualquer outro é local. Ids: local `agent-<uuid>`, cloud `bc-<uuid>`, preenchidos na criação. `agent.model` fica `undefined` no resume se `model` não for passado de novo. `mcpServers` inline não persistem; é preciso passá-los de novo, ou usar `.cursor/mcp.json` com `local.settingSources`. `tools` / `disallowedTools` também não persistem. `systemPrompt` não persiste. — [typescript.md](https://cursor.com/docs/sdk/typescript.md) (Resuming agents, Restricting the toolset, system prompt)
- `RunResult`: `id`, `requestId?`, `status` (`finished` | `error` | `cancelled`), `result?: string`, `error?`, `model?`, `durationMs?`, `usage?`, `git?`. `requestId` é UUID por `agent.send()`. `run.conversation()` devolve `ConversationTurn[]` daquele run (turno de agente com steps, ou turno de shell com command e output). Não há campo “conversation id” separado de `agentId` / `run_id` / `requestId` nessa página. `agent.send(texto)` no mesmo handle continua a conversa. `run.steer(text)` injeta texto no turno que já corre (local em primeiro plano); `revert_to_followup` manda entregar depois com `agent.send`. — [typescript.md](https://cursor.com/docs/sdk/typescript.md)
- Evento de stream `"request"`: “Awaiting user input or approval”, campo `request_id`. `RunOperation` é só `"stream" | "wait" | "cancel" | "conversation"`. A página não documenta um método que responda a esse `request_id`. Agente local default executa shell/edit/write sem pedir aprovação: “there's no human-in-the-loop prompt in headless mode.” — [typescript.md](https://cursor.com/docs/sdk/typescript.md) (Quickstart approves tool calls automatically, stream events, sandbox)
- No starter, etapa local cria agente com `Agent.create` a cada tentativa (`localBackend`). `Agent.resume` no código do kit está no backend de cloud, para reanexar o agente que uma tentativa interrompida deixou (`resumeInterrupted`); se o agente sumiu ou o run foi cancelado, a tentativa cria outro. — [backend.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/backend.ts), [backend-cloud.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/backend-cloud.ts)
- Journal do starter: append-only, chave `sha256(prompt + "\0" + JSON.stringify(fingerprint))` mais índice de ocorrência desse hash. Fingerprint: `model`, `schema`, `cwd`, `tools`, `disallowedTools`, `agents`, `settingSources`. Hit devolve `cached.result` e não chama a API. O comentário do arquivo contrasta com o Claude Code: lá o cache de resume segue a ordem de início dos `agent()`; aqui reordenar por `pipeline()` não invalida etapas já gravadas, e editar o prompt de uma etapa reexecuta essa etapa e as cujo prompt mudou por depender do resultado novo. Segredo é redatado antes de gravar; o resume reapresenta a cópia redatada para a chave das etapas seguintes bater. Linha rasgada é ignorada e a etapa roda de novo. Retenção apaga `result`, marca `pruned: true`, e um resume desse journal é recusado. — [journal.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/journal.ts), [engine.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/engine.ts)
- Estado em disco: `.workflows/runs/<runId>/` com `events.jsonl`, `journal.jsonl`, `run.lock`; jobs em `.workflows/jobs/<jobId>.json` mais `<jobId>.log`. O registro do job guarda identidade e o que o log não guarda (args do start, recusa, marca de kill). `status` / `phase` / `recent` / `result` vêm do log. Heartbeat 5 s; sem heartbeat por 30 s o job aparece `failed`, com texto que inclui o `runId` para retomar. — [03-conceitos.md](file:///home/rodrigo/Workspace/cursor-workflows-starter/docs/vision/03-conceitos.md), [job-state.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/job-state.ts)
- `start_workflow.resumeRunId` (e `wf start --resume` / `wf run --resume`) continua o mesmo run. A descrição da tool: “runId of an earlier run (one that failed, or stopped at a checkpoint and returned `next`), to resume it without repeating finished steps”. Um `resumeRunId` dentro de `args` não retoma. — [mcp-server.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/mcp-server.ts), [SKILL.md run-workflow](file:///home/rodrigo/Workspace/cursor-workflows-starter/skills/run-workflow/SKILL.md)
- Checkpoint observado no `implement-issue`: o run não fica bloqueado à espera. Grava o plano em `progress.data.proposedPlan`, devolve objeto com `status: "seams-proposed"` ou `"test-command-proposed"`, `runId`, `seams`, `slices` e `next` (comando `wf run ... --resume <runId>` com os args de aprovação). O job termina `finished`. A skill manda o agente do chat mostrar seams/slices e perguntar; com a aprovação, novo `start_workflow` com os mesmos `name`, args acrescidos (`approveSeams: true`, ou `seams` / `testCommand` / `allowExternalAuthor`) e `resumeRunId: result.runId`. No resume, `approveSeams` sem `seams` e com `proposedPlan` usa esse plano e não chama o planejador de novo; sem o plano gravado, devolve `seams-not-proposed`. Comentário no código: “A person's decision on the proposed seams … reaches the run as a resume, from the chat, the CLI or the dashboard.” — [implement-issue.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/workflows/implement-issue.ts), [SKILL.md run-workflow](file:///home/rodrigo/Workspace/cursor-workflows-starter/skills/run-workflow/SKILL.md)
- Cursor documenta MCP Elicitation (“Server-initiated requests for additional information from users”) como capability do cliente. O `mcp-server.ts` do kit não chama elicitation: o gate é o JSON `result` + um turno novo do chat. — [mcp.md](https://cursor.com/docs/mcp), [mcp-server.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/mcp-server.ts)

### Inferences
- Inferência: um turno posterior do IDE consegue entregar a resposta, mas só como args de um start novo no mesmo `runId`. Não há API no kit que faça `agent.send(respostaDoUsuario)` no agente que explorou. Etapas cujo `agent()` for chamado de novo com o mesmo prompt e fingerprint saem do journal; o desvio do gate em si é `if` no código do workflow mais o arquivo de progresso, não uma conversa suspensa.
- Inferência: `RunResult.id` / `requestId` / `agent.agentId` não são o `runId` do workflow. Passar o `agentId` de uma etapa ao chat não retoma o workflow.

### Gaps
- Como um host responde ao evento SDK `"request"` (`request_id`). A página lista o evento e não lista um método de resposta.
- Se o dashboard, ao retomar, grava os mesmos args que o chat. O comentário do workflow cita o dashboard como origem do resume; o corpo do `decideSeams` não foi o foco desta leitura além do que está citado.

## Como os workflows do Claude Code pausam para uma pessoa e retomam (phase, journal, o padrão do deep-research: pesquisadores e depois um relatório). Não copiar essa API para o Cursor

### Takeaway
No Claude Code o script segura os resultados intermediários; a sessão recebe um relatório no fim, não o transcript. Não há journal por hash. A pausa espontânea do run é prompt de permissão ou espera de limite de uso. Entrevista entre etapas não existe dentro do run: a doc manda um workflow por etapa. `/deep-research` faz fan-out, checagem e um relatório citado, com a sessão livre no meio. Isso não é `resumeRunId` nem `Agent.resume`.

### Cited Findings
- “A dynamic workflow is a JavaScript script that orchestrates many subagents.” O runtime executa o script em ambiente isolado, separado da conversa. “Intermediate results stay in script variables instead of landing in Claude's context.” “Claude's context holds only the final answer.” Quem decide o próximo passo é o script, não o Claude turno a turno. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (When to use a workflow, How a workflow runs)
- `phase(title)` agrupa no progresso os `agent()` seguintes. `meta.phases` deve repetir esses títulos. `log()` mostra mensagem acima das fases. `Date.now()`, `Math.random()` e `new Date()` sem argumento lançam dentro do script, para um relaunch repetir os mesmos `agent()`. Timestamp entra por `args`. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (Edit a saved script)
- `schema` em `agent()` faz o subagent devolver JSON. Schema autocontraditório falha antes de iniciar. Saída inválida: até cinco tentativas (`MAX_STRUCTURED_OUTPUT_RETRIES`). `agent()` resolve `null` se parado no meio ou em erro de API irrecuperável. — [workflows.md](https://code.claude.com/docs/en/workflows.md)
- Limite “No mid-run user input”: “A run pauses on its own only for agent permission prompts and a usage-limit wait. For sign-off between stages, run each stage as its own workflow.” O script não tem filesystem nem shell; quem lê e executa comando é o agente. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (Behavior and limits)
- Retomada: em `/workflows`, `p` pausa ou retoma. Run parado: pedir ao Claude para relançar o mesmo script. O runtime “tracks each agent's result”, e no relaunch “each agent either returns its saved result or runs again”, na ordem em que os agentes começam. Completed devolve o resultado salvo. O primeiro cujo prompt difere (script editado ou resultado anterior diferente) roda de novo, e todo agente depois dele também, mesmo os que tinham completado. Still running ao parar: começa de novo. Failed: roda de novo e todos os posteriores. Não há arquivo chamado journal nem chave por hash nessa página. Resultados ficam no diretório da sessão em `~/.claude/projects/`. Sem eles, o relaunch falha com `nothing to resume` em vez de recomeçar sozinho. Sair da sessão não continua o run; continua quando o Claude relança com uma chamada `Workflow`. `claude --resume` recupera a sessão, e então se pede o relaunch. Sessão nova não acha o run anterior. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (Resume after a pause, Which agents run again)
- Espera de limite de uso (v2.1.271+, ou v2.1.319+ na Code tab) pausa o run em sessão interativa elegível; não pausa em `claude -p`, Agent SDK, background, Remote Control, SSH, WSL, Dispatch, tarefa agendada. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (When a run hits your usage limit)
- `/deep-research <question>`: agentes passam por fases em background, “your session stays free”, “one report at the end instead of a turn-by-turn transcript”. Fan-out de buscas web, fetch, cross-check, voto por claim, relatório citado; claim não checada por rate limit ou erro de API fica “unverified”, não refutada. Exige a tool WebSearch. Só roda quando invocado. A página não publica o script, os títulos de `phase()`, nem papéis “researcher” / “report writer”. — [workflows.md](https://code.claude.com/docs/en/workflows.md) (Run a bundled workflow, Bundled workflows)
- O protocolo de notas desta pesquisa (pesquisadores escrevem notas; um report writer sintetiza e não pesquisa de novo) está em `deep-research/references/researcher.md`. Isso é contrato da skill, não a API de pause/resume do runtime descrita em `workflows.md`. — [researcher.md](file:///home/rodrigo/.claude/skills/synced/7490ada9-9a56-490d-8cd7-bb790fb0da33_77e381c8-107f-499a-829b-0f985d492ff6/deep-research/references/researcher.md)
- O próprio `journal.ts` do starter avisa a diferença: no Claude o resume segue “o maior prefixo inalterado de agent() na ordem de início”; no starter a chave é hash do prompt e das opções mais a ocorrência. — [journal.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/journal.ts)

### Inferences
- Inferência: no Claude Code, uma entrevista entre “pesquisadores” e “relatório” não é um checkpoint do mesmo run. A frase prescrita da doc é outro workflow para o sign-off. O relatório único do `/deep-research` chega na sessão porque o run terminou, não porque um `wait` devolveu estado parcial.
- Inferência: copiar `phase()`, `agent()` ou “saved result por ordem de início” para o starter misturaria mecanismos. No starter, `phase` é rótulo de progresso no `JobState`; a memória de etapa é o journal por hash; a entrevista é um `return` com `next`.

### Gaps
- O script de `/deep-research` (quantos agentes, títulos de fase, se grava arquivos de notas). A página de workflows não o inclui. Não foi aberto o fonte do pacote Claude Code.

## Quais ferramentas de exploração um agente local do SDK pode chamar (MCP do projeto, shell, web) e quais existem só na sessão do IDE (namespace MCP do Cursor, computer use, browser do IDE)

### Takeaway
O agente local do SDK tem o toolset do runtime (shell, leitura, `webSearch`, MCP carregado por `mcpServers` / `settingSources`, subagents via `task`). Ele não está ligado aos servidores que o chat do IDE tem na sessão. O browser nativo do IDE é ferramenta do Agent do IDE. Computer use aparece em eventos do SDK e numa flag de worker da CLI; a página do SDK não o lista entre os nomes públicos de tool, nem descreve o browser embutido.

### Cited Findings
- Toolset local, nomes públicos citados: `"read"`, `"edit"`, `"task"`, `"webSearch"`, grupos `"shell"` e `"mcp"`, mais nomes proto. `ToolCall` cobre shell, edit, read, write, glob, grep, ls, semSearch, mcp, task, “and others”. `tools: undefined` oferece o toolset padrão do modelo; `tools: []` só texto. Allowlist e denylist são só de agente local e não persistem no `Agent.resume`. — [typescript.md](https://cursor.com/docs/sdk/typescript.md) (Restricting the toolset, ToolCall)
- MCP do agente local, primeira ocorrência do nome ganha: (1) `mcpServers` no `send` substitui os do create, não mescla; (2) `mcpServers` no `Agent.create`; (3) plugins se `settingSources` inclui `"plugins"`; (4) `.cursor/mcp.json` se inclui `"project"`; (5) `~/.cursor/mcp.json` se inclui `"user"`. Sem `settingSources`, só os inline. OAuth local não abre browser: só reusa login já feito no app Cursor. ## O que permanece não determinístico (a busca do modelo) e o que o orquestrador fixa em código (quais fontes, o schema do resultado, quando parar e perguntar)

### Takeaway
A escolha do que ler, buscar ou citar, dentro das tools liberadas, é do modelo. O orquestrador fixa a allowlist, os MCP, o schema, o texto do prompt, a fase, e o `return` que encerra o job e pede outra invocação. Isso está nas APIs; não é uma propriedade medida da qualidade da busca.

### Cited Findings
- Etapa do starter: `tools` é allowlist (`["read","grep","glob","ls"]` no comentário para leitura). `schema` com `type: "object"` obriga a tool `submit_result`; o retorno da etapa é o objeto validado. Sem schema, o retorno é o texto final. `schemaRetries` default 2 quando o agente não chama a tool ou manda JSON inválido. `settingSources` escolhe as camadas (projeto, usuário, time, plugins). `mcpServers` é por chamada. `memo: true` só com tools de leitura, e devolve resultado salvo se prompt, modelo, schema, tools e estado do git coincidirem, sem chamar a API. — [workflow.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/workflow.ts)
- Parar e perguntar, no kit, é código: o workflow `return`a um objeto (`status`, `next`, payload). O processo acaba com `run-end` `finished`. Não há primitiva “pause até o usuário” no engine. A pergunta acontece no chat porque a skill lê `result.next`. — [implement-issue.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/workflows/implement-issue.ts), [engine.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/engine.ts), [SKILL.md run-workflow](file:///home/rodrigo/Workspace/cursor-workflows-starter/skills/run-workflow/SKILL.md)
- SDK: “The Cursor SDK is an agent SDK, not a standalone model-inference or chat-completions API.” O modelo da etapa chama tools. O host não escolhe a sequência de greps. `tools` restringe o que é oferecido. — [typescript.md](https://cursor.com/docs/sdk/typescript.md) (overview e Restricting the toolset)
- Claude Code, mesmo corte, outra API: o script escolhe os `agent()`, o `schema` e o `phase()`; “No mid-run user input” impede a pessoa de redirecionar a busca no meio; resultados intermediários ficam em variáveis do script; a sessão fica com a resposta final. `/deep-research` fixa o padrão (vários ângulos, cross-check, um relatório) e deixa as buscas aos agentes, que precisam de WebSearch. — [workflows.md](https://code.claude.com/docs/en/workflows.md)

### Inferences
- Inferência: para o objetivo “o chat recebe o resultado pronto e o agente do IDE continua”, o contrato estável é o JSON de `result` no `JobState` (ou o `RunOutcome` de `wf run`), não o transcript da etapa. Para “parar, entrevistar, retomar”, o contrato estável no starter é `status` + `next` + `resumeRunId` + args novos; no Claude Code é um segundo workflow, ou um relaunch do mesmo script, não um journal compartilhado com o Cursor.

### Gaps
- Nenhuma métrica, nesta leitura, de quanto a allowlist reduz variância da busca. As APIs dizem o que é imposto; não dizem o quanto o modelo ainda varia dentro disso.
