# Nomear a camada aproxima o passo

Um passo do `cursor-workflows-starter` fica perto de um turno do Cursor IDE só na fatia de disco que `local.settingSources` nomeia, e essa fatia não é a sessão. No `@cursor/sdk` **1.3.1**, omitir `local.settingSources` ou passar `[]` deixa `project`, `user`, `team`, `mdm` e `plugins` desligados: o parser não monta regras, skills, hooks nem MCP de arquivo ([305.js](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/305.js), [TypeScript SDK](https://cursor.com/docs/sdk/typescript.md)). O checkout **`12cba8f`** (2026-11-17, árvore limpa em `main`) não herda esse vazio. Quando o campo chega `undefined`, o engine grava **`["project", "team", "mdm"]`** antes do `Agent.create` ([repo-code.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/repo-code.ts), [engine.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/engine.ts)). **`project` lê o checkout** — `.cursor/rules/*.mdc`, `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.cursorrules`, hooks e `.cursor/mcp.json` do workspace, mais skills e subagents desse workspace — e **não é a sessão do IDE**: User Rules da conta, Team Rules do dashboard, o corpo de uma skill que só entra com `/nome`, os MCP ligados só no chat e os subagents de `~/.cursor/agents` ficam de fora. No cloud o array local é descartado; a VM carrega `project`, `team` e `plugins`, e `user` e `mdm` não têm equivalente. Exploração volta ao chat como o `result` do `JobState`. Entrevista é um job que termina com `next` e um segundo `start_workflow` no mesmo `resumeRunId`. Não há skill de exploração de banco no disco; a forma alvo (MCP, CLI, ramos no estilo `--review` e `--interview`) vira enum em `ctx.args` quando a regra é objetiva, e diálogo aberto permanece skill. O Claude Code carrega instrução de projeto salvo opt-out e não aceita a pessoa no meio do run; o mecanismo é outro.

## Lista vazia zera o disco e o kit preenche três nomes

`Agent.create` e `Agent.resume` não têm `rules`, `instructions` nem `system` separado. O único texto de sistema é `systemPrompt`, e ele **substitui** o prompt interno do harness; schemas de tools e o contexto ambiente (rules, skills, `<user_info>`) continuam, subagents de `"task"` mantêm o prompt deles, o valor não persiste no resume, string vazia lança `ConfigurationError`, e com `cloud` também ([options.d.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/node_modules/@cursor/sdk/dist/esm/agent/options.d.ts), [TypeScript SDK](https://cursor.com/docs/sdk/typescript.md)). O acesso é por conta. O `.d.ts` e a página divergem no texto exato do erro, e esta leitura não confirmou qual string o backend devolve. O runtime do starter **não seta** `systemPrompt`. O texto do `ctx.agent` vai na mensagem de `send`, e, quando há `schema`, o backend concatena a instrução da tool `submit_result` ([backend.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/runtime/backend.ts)). `defineWorkflow` devolve o objeto sem validar. `phase` só nomeia o progresso. `parallel` e `pipeline` agrupam chamadas. O comentário do kit que descreve o default como “AGENTS.md, rules, hooks e MCP do projeto, mais regras e hooks de time” atribui ao nome `team` um merge que este cliente não mostra. O que `team` chega a ser, neste binário, é sync de skill gerenciada, não Team Rule do dashboard.

## Project lê o checkout e a sessão fica de fora

No IDE, as regras de conversa do Agent são Project Rules em `.cursor/rules/*.mdc`, User Rules, Team Rules e `AGENTS.md`, com `CLAUDE.md` e `CLAUDE.local.md` lidos como `AGENTS.md`, mais o legado `.cursorrules` ([Rules](https://cursor.com/docs/rules.md), [Help](https://cursor.com/help/customization/rules.md)). A frase de conflito escrita é **Team Rules, depois Project Rules, depois User Rules**: todas as aplicáveis se mesclam e a fonte anterior prevalece. `AGENTS.md` aninhado não entra nessa frase; o mais específico prevalece sobre o pai. Um `.md` solto em `.cursor/rules` é ignorado. `alwaysApply: true` entra sempre. Com `globs`, a rule entra quando um arquivo que casa está no contexto. Com `description` e sem globs, o Agent puxa quando acha relevante. Sem os dois, só com `@`. Menção `@arquivo` dentro da rule não inline o arquivo. User Rules de Customize ficam na conta, sincronizam no login e não entram em profile export. Arquivos em `~/.cursor/rules` ficam na máquina e não sincronizam. Team Rules são texto livre no dashboard, com glob opcional; “Enforce this rule” não pode ser desligada em Customize. A página de regras **não** coloca `AGENTS.md` nem `CLAUDE.md` nessa ordem de três, e não há fonte para inventar a posição.

O walker do pacote, com `project`, sobe do workspace até a raiz do filesystem e em cada nível lê `.cursor/rules` e `AGENTS.md`. O executor passa `getThirdPartyExtensibilityEnabled: () => true`, então `CLAUDE.md` e `CLAUDE.local.md` entram junto, sem consultar o toggle Third-Party Imports do IDE (o doc do IDE diz que o default desse toggle é ligado, e o usuário pode desligar). Markdown desses nomes é gravado com `alwaysApply: true`. Arquivo acima de **102400 bytes** é cortado no prefixo dos primeiros 100 KB. Só `.mdc` sob `.cursor/rules` entra na classe rules. Duplicata de inode ou de texto trimmed, com um path sob o outro, fica uma; no mesmo nível, `AGENTS.md` vem antes de `CLAUDE.md`, então a cópia idêntica cai. Texto diferente chega duas vezes. O filtro de realpath descarta arquivo lido num ancestral fora dos workspace roots, então `~/AGENTS.md` não sobrevive ao layer `project` quando o cwd é um subdiretório. `.cursorrules` é lido no git root, senão no root do workspace, com `alwaysApply: true`. A precedência Team → Project → User é política do produto. O walker não a implementa. Não há fetch de User Rules da conta no builder `Cr`. Não há walker confirmado de `~/.cursor/rules/*.mdc` no layer `user`; os diretórios de usuário explícitos nesse trecho são de skills. A ajuda afirma que a pasta existe. O cliente publicado não busca Team Rules. Um slot `cloudRulesService.getCloudRule` existe e `Cr` não o preenche.

A alegação de que o Cursor não lê `CLAUDE.md` está refutada na ajuda ao vivo e no walker: com `project` e third-party forçado, o arquivo é carregado. O que esta leitura não mediu é se uma rule `alwaysApply: true` entra no prompt de todo turno headless ou só fica disponível para o modelo puxar. O IDE diz “included”. O pacote mostra o load. Glob quando o passo não abre arquivo também não foi medido, e o SDK não oferece override para forçar o glob. Rule “Apply Manually” só entra com `@`, e `AgentOptions` não tem menção.

Skills seguem o mesmo opt-in, com um segundo corte entre catálogo e corpo. O IDE descobre `SKILL.md` em `.agents/skills/`, `.cursor/skills/`, as pastas de home, e as de compatibilidade `.claude/skills/` e `.codex/skills/`, e apresenta as skills ao agente; o corpo entra quando a skill é invocada. `/nome` anexa a skill à mensagem. Custom Mode a mantém na sessão. `disable-model-invocation: true` faz a skill só entrar com `/skill-name` ([Agent Skills](https://cursor.com/docs/skills.md)). A página de prompting do IDE diz que as descrições vão no contexto de sistema ([Prompting](https://cursor.com/docs/agent/prompting)). Combinar `subagentInherit` com `fs` lança `ConfigurationError`. O kit só repassa `agents` se a chamada passar.

MCP local, primeira ocorrência do nome ganha: `mcpServers` do `send` substitui o do `create`; depois plugins se `"plugins"`; depois `.cursor/mcp.json` se `"project"`; depois `~/.cursor/mcp.json` se `"user"`. Sem `settingSources`, só inline ([TypeScript SDK](https://cursor.com/docs/sdk/typescript.md)). O kit coloca `mcpServers` no `create`. O `send` leva só `onDelta`, embora `SendOptions` aceite mais. Dentro da etapa o servidor de workflows sobe com mapa vazio. O chat não encaminha o browser embutido nem os namespaces MCP do processo do IDE. ## O chat puxa o JSON e a entrevista abre outro job

O job é outro processo. Não escreve no chat. O servidor MCP `cursor-workflows` registra, fora da etapa, `list_workflows`, `start_workflow`, `wait_workflow`, `get_workflow_status` e `cancel_workflow`, e responde com um bloco `text` de JSON ([mcp-server.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/src/mcp-server.ts)). `start_workflow` devolve na hora `{ jobId, runId, next, dashboardUrl? }` e não espera o run. `wait_workflow` espera no máximo **50 s** (ausente ou `null` vira **45**) e devolve o `JobState`. `wf run` em primeiro plano imprime o `RunOutcome`; `wf status` e `wf wait` imprimem o mesmo estado. Quem fala depois da tool é o modelo do chat. A skill `run-workflow` manda, enquanto `status` é `running`, encadear `wait_workflow` e mostrar `phase` e linhas novas de `recent`; quando termina, apresentar `result`. Cada espera é uma tool call desse modelo e gasta tokens dele. Run Mode pode pedir aprovação entre esperas. `postToolUse` pode injetar `additional_context` ou substituir a saída MCP ([Hooks](https://cursor.com/docs/hooks.md)).

`recent` guarda **20 linhas**, cada uma com no máximo **200 caracteres**, a partir de metadados, `ctx.log` e warnings. O `result` é o retorno de `def.run`, inteiro, sem o corte de `recent`. O event log lido para o estado omite eventos `content` (prompt e texto de agente). Não há teto de bytes documentado para esse JSON na página de MCP do IDE; o FAQ só diz que servidor caído ou estourado marca a chamada como falha. No stream do SDK, `tool_call` pode vir com `truncated` sem limiar publicado. `ctx.exec` devolve os últimos **32768** caracteres para dentro do processo do workflow; isso só chega ao chat se o workflow colocar o texto no valor retornado. Reiniciar o servidor MCP ou o Cursor não mata o job.

Não há status `paused`. Os finais do engine são `finished`, `failed` e `cancelled`. Recusa de args, antes do log, é `failed` com `refused`. Parar para perguntar é o workflow dar `return` num objeto com `status`, `runId`, payload e `next`. O processo acaba `finished`. O exemplo medido no desenho, não nesta sessão, é o checkpoint de `implement-issue`: grava o plano, devolve `seams-proposed` ou `test-command-proposed`, e o `next` traz o comando de resume. A skill manda o agente do chat mostrar seams e perguntar. Com a resposta, um `start_workflow` novo leva os mesmos `name`, os args acrescidos (`approveSeams`, ou `seams` / `testCommand`) e **`resumeRunId`**. Um `resumeRunId` dentro de `args` não retoma. No resume, `approveSeams` sem `seams` e com `proposedPlan` usa o plano e não chama o planejador de novo; sem o plano, devolve `seams-not-proposed` ([implement-issue.ts](file:///home/rodrigo/Workspace/cursor-workflows-starter/packages/runtime/workflows/implement-issue.ts)). A página de MCP do Cursor documenta elicitation, pedido do servidor ao usuário. O `mcp-server.ts` não chama essa capability.

São duas retomadas. `Agent.resume(agentId)` religa um agente do SDK (`agent-<uuid>` local, `bc-<uuid>` cloud). `mcpServers` inline, `tools` e `systemPrompt` não persistem. O kit usa esse resume no backend cloud para reanexar uma tentativa interrompida. O `runId` do workflow é outro id. Passar o `agentId` de uma etapa ao chat não continua o `def.run`. A resposta da pessoa entra como args de um start novo no mesmo `runId`. Etapa `agent` já concluída volta do journal sem `Agent.create` quando a chave bate: SHA-256 do prompt mais fingerprint (`model`, `schema`, `cwd`, `tools`, `disallowedTools`, `agents`, `settingSources`) mais o índice de ocorrência. **`mcpServers` e `sandbox` ficam fora da chave.** Um resume pode devolver o resultado velho se só esses dois mudaram. `ctx.exec` não entra no journal; o resume roda o comando de novo. Editar o prompt reexecuta aquela etapa e as que passam a depender do resultado novo. Retenção (default últimas 30 runs ou 14 dias) apaga o `result` do journal e recusa o resume. Cancelamento deixa o journal das etapas concluídas e a mensagem pede `resumeRunId`. Heartbeat parado 30 s mostra o job `failed` com a mesma dica.

O que o passo pode chamar, dentro da allowlist, é o toolset do runtime: `read`, `grep`, `glob`, `ls`, `semSearch`, o grupo `shell`, o grupo `mcp`, `webSearch`, `webFetch`, `task`. A escolha do que ler, buscar ou citar, dentro disso, é do modelo. O SDK é um agent SDK, não uma API de chat-completions: o host não escolhe a sequência de greps ([TypeScript SDK](https://cursor.com/docs/sdk/typescript.md)). O orquestrador fixa a allowlist, os `mcpServers`, o `schema`, o texto do prompt, a `phase` e o `return`. `schema` com `type: "object"` obriga `submit_result`; `schemaRetries` default **2**; sem schema o retorno é o texto final. `memo: true` só com tools exclusivamente de leitura e cwd git, e devolve sem API se prompt, modelo, schema, tools e o estado do git coincidem; cloud não memoriza; um CLI com efeito não pode usar memo. Não há métrica, nestas notas, de quanto a allowlist reduz a variância da busca.

Sandbox default do SDK é desligado: o agente lê e escreve o cwd, com shell e rede, sem aprovação. O template do kit força sandbox por OR. Na medição de 2026-11-14, com `sandbox: true` e `readBoundary: "workspace"`, escrita fora do repositório foi bloqueada no shell e na tool `edit`, e a leitura de `~/.cursor/sdk/auth.json` só foi recusada com esse `readBoundary` (sem o campo, o mesmo `cat` saiu 0). Sem sandbox, uma etapa com `shell`/`edit` alterou um arquivo fora do repositório. Exploração que dá `"shell"` ao agente reabre esse ramo; o script que já sabe o comando usa `ctx.exec`.

## Review vira enum e a entrevista aberta fica skill

Não há no disco um `SKILL.md` de exploração de banco. A busca por `database-explor` / `db-explor`, por `--review` em skills de `/home/rodrigo/.claude/skills`, e pelos globs de exploração e de banco não achou essa skill. No repositório alvo o módulo é objeto plano `{ meta, defaults, budget, run }`. `defineWorkflow` é a forma dos workflows do kit e não acrescenta validação. `argument-hint` não é schema e não chega ao runtime. Na página de skills do Cursor ele não existe; os campos que mudam o fluxo são `description`, `paths` e `disable-model-invocation`. Flag desconhecida sai com código 2. `wf run explore --review` nem chega ao script. O ramo determinístico é `wf run explore --args '{"mode":"review"}'` com `argsSchema` exigindo um enum. Os nomes `review` e `interview` aqui são ilustração da forma, não um schema encontrado. Ajv (`allErrors`, `strict: false`) recusa o run antes do log e antes do job, no handler de `start_workflow` e no start do dashboard. `list_workflows` devolve o `meta` inteiro, então o modelo do chat vê o `argsSchema`. `wf list` devolve só `name` e `description`. No chat, o modelo que chama `start_workflow` ainda traduz a frase da pessoa no objeto. Essa tradução acontece uma vez, na tool, e o Ajv corta o objeto inválido antes da primeira etapa.

Na forma alvo, o script escolhe o modo pelo enum, dispara os CLI de inspeção com `ctx.exec` no ramo, e restringe `mcpServers` ao servidor daquela etapa. “Qual tool MCP chamar e com quais argumentos” continua turno do modelo: não há `ctx.mcp(nome, args)` no runtime lido. `local.customTools` seria chamada tipada no processo host, ainda disparada pelo modelo, e o kit só expõe isso como `submit_result`. Para `--interview`, diálogo aberto fica skill. O texto de cada pergunta, se não for constante no código, continua modelo. O momento da pausa é o `return`. `askQuestion` está no union `ToolName` e a skill de conversão não mapeia “ask” para essa tool. Se ela pausa um agente local headless não foi verificado.

## O Claude Code carrega salvo opt-out e não pergunta no meio

O default é o inverso, e a pausa também. `claude -p` sem `--bare` descobre hooks, skills, commands, subagents, plugins, MCP, auto memory e `CLAUDE.md` como uma sessão interativa, inclusive em pasta não trusted, sem diálogo de trust. `--bare` pula essa descoberta (com a exceção parcial de skills em `--add-dir`) e a página diz que esse modo é o recomendado para script e SDK e passará a ser o default de `-p` ([Headless](https://code.claude.com/docs/en/headless.md)). Rules de projeto são puladas se `project` está fora de `--setting-sources`. A ordem de `CLAUDE.md` começa no managed (`/etc/claude-code/CLAUDE.md` em Linux e WSL), segue o user em `~/.claude/CLAUDE.md` e depois o projeto. Ancestrais são concatenados da raiz até o cwd. Subdiretórios carregam quando o Claude lê ou edita um arquivo lá. O modo default `claude-md-or-agents-md` lê `AGENTS.md` só na ausência de `CLAUDE.md`, `.claude/CLAUDE.md` ou `CLAUDE.local.md` no cwd ou acima. Os dois juntos exigem `claude-md-and-agents-md`, com dedup de import e de inode ([Memory](https://code.claude.com/docs/en/memory.md)). O walker do Cursor, com third-party forçado, carrega os dois e só deduplica texto ou inode iguais. Um `CLAUDE.md` que faz `@AGENTS.md` é import no Claude Code. A ajuda do Cursor não descreve esse `@` como import, e o pacote não mostra o expand. Rules com glob no Claude Code usam `paths` em `.claude/rules/*.md` e ignoram outro frontmatter. O Cursor IDE usa `globs`, `alwaysApply` e `description` em `.mdc`. O SDK não traduz um no outro.

Um `agent()` de dynamic workflow é um subagent. A página de subagents diz que ele recebe a hierarquia de `CLAUDE.md` que a sessão carregou, com Explore, Plan e `omitClaudeMd` como exceções, e a mesma página diz noutro ponto que `CLAUDE.md` ainda entra pelo fluxo de mensagens mesmo com `omitClaudeMd`. As duas frases foram baixadas em 2026-11-17 e ficaram sem terceira fonte ([Sub-agents](https://code.claude.com/docs/en/sub-agents.md)). A página de workflows não nomeia `omitClaudeMd` nem `--setting-sources` no `agent()`. O prompt de subagent custom substitui o system prompt default, no mesmo sentido de `--system-prompt`, e a instrução permanente que soma é `--append-system-prompt`. O Cursor SDK tem só o substituto, local, com gate de conta. Admin também diverge: Team Rules do Cursor são dashboard, com precedência sobre project e user; hooks MDM são `/etc/cursor/hooks.json` no layer `"mdm"`. O Claude Code tem `CLAUDE.md` managed e settings managed que vencem user e project. Não há `CLAUDE.md` managed do Cursor no cliente do SDK.

O script do workflow Claude Code não chama shell nem filesystem; os agentes leem e executam. Não há entrada da pessoa no meio do run: a pausa espontânea é prompt de permissão ou espera de limite de uso, e essa espera não ocorre em `claude -p`, Agent SDK, background, SSH, WSL nem tarefa agendada. Sign-off entre etapas é outro workflow. Resultados intermediários ficam em variáveis do script; o contexto da sessão fica com a resposta final. Não há journal por hash. No relaunch, cada agente devolve o resultado salvo ou roda de novo na ordem de início; o primeiro cujo prompt difere reexecuta, e todo agente depois dele também. `/deep-research` faz fan-out em background, deixa a sessão livre e entrega um relatório no fim, com claim não checada marcada “unverified”. A página não publica o script nem papéis “researcher” / “report writer” ([Workflows](https://code.claude.com/docs/en/workflows.md)). O protocolo de notas desta pesquisa é contrato da skill, não essa API. Cache de prefixo entre irmãos, com espera de até `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS` (default 5000) e TTL de 5 min ou 1 h, não existe como controle no SDK do Cursor. Copiar `phase()`, “saved result por ordem de início” ou a ausência de shell para o starter misturaria os dois runtimes: no starter, `phase` é rótulo no `JobState`, a memória de etapa é o hash, o shell do script é `ctx.exec`, e a entrevista é um `return` com `next`.

## Conclusion

O que muda no desenho é o slot de cada instrução. Texto que tem de valer em todo run do SDK e que hoje vive só na conta (User Rules de Customize, Team Rule enforced) não tem campo nem fetch neste cliente: ou ele está num `AGENTS.md` / `.mdc` com `alwaysApply: true` que `project` carrega, ou está no prompt da etapa, ou o passo é fiel ao checkout e omisso em relação à pessoa. `[]` numa etapa de leitura e `project` numa etapa que julga são políticas diferentes de propósito, e o `??` é o que faz a lista vazia vencer o default do `12cba8f`. O cloud não serve de alvo de paridade para `user`, `mdm`, allowlist ou `systemPrompt`.

Exploração que devolve o trabalho pronto põe o artefato no `return`, porque `recent` é capado e o transcript da etapa não viaja no `JobState`; o chat não reconstrói a busca. Exploração que precisa perguntar termina o processo: `Agent.resume` responde outro id e não continua o `def.run`. Na forma alvo, CLI e escolha de servidor e o enum do modo viram o script; entrevista aberta fica skill, nomeada no relatório de conversão; questionário finito são dois jobs `finished`. O que permanece modelo, de propósito, é o julgamento do achado e a tool dentro do servidor MCP. A tradução da frase da pessoa em `args` continua um turno do chat, uma vez, com o Ajv na frente. Velocidade e custo seguem esse corte — não chamar o agente quando o ramo já está em `ctx.args` — e os centavos de 2026-11-11 permanecem estimativa. Um port do mesmo skill para o Claude Code usa o opt-out ao contrário e um segundo workflow para o sign-off; um módulo compartilhado codaria a pausa errada.
